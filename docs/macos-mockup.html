Sunno for macOS

Same product shape as the Windows app, rebuilt in the macOS control vocabulary. Layout, information architecture and every feature are unchanged. What changes is the widget set, the icon set, the type ramp and where the system expects commands to live. Three places where a macOS pattern genuinely conflicts with the Windows shape are flagged in orange and need a decision.

1. Main window NSSplitViewController + NSHostingView

Sidebar gets the standard .sidebar vibrancy material and rounded selection. The bottom command bar survives as-is, which is slightly unusual for macOS but is the right call here: it keeps the level meter beside the device that owns it, exactly as the WinUI comment argues.

2. Compact mode NSPanel, .floating level

Same idea as Windows: captions only, always on top, its own remembered geometry. On macOS this becomes a genuine NSPanel rather than a resized window, which gets non-activating behaviour for free, so clicking the captions does not steal focus from the app you are actually in. That is a small win over the Windows build.

Decision 1. On Windows these live in a "…" overflow button. On macOS they belong in the menu bar under View and Window, where the system already draws checkmarks and accelerators. Keeping the overflow button as well is defensible for discoverability, but the menu bar versions have to exist either way.

3. Settings Settings scene, ⌘,

Decision 2. The Windows build makes Settings a full-window page with a back arrow, matching the Windows inbox apps. macOS expects a separate window opened with ⌘, with a toolbar of tabs, and users will look in the app menu for it. Shown here the macOS way. Keeping the full-window page instead is possible, but it would be the most obviously non-native thing in the app.

4. First run window content, not a sheet

Kept as full window content rather than a sheet, because there is nothing behind it yet and a sheet implies something to go back to. List becomes an inset grouped list with real macOS radio buttons. The per-machine delay estimate stays, which is the whole point of the screen, and on Apple Silicon it will finally have measured numbers behind it.

5. Menu bar new on macOS, no Windows equivalent

Windows has no menu bar, so this is additive rather than a mapping. Every command currently in the overflow flyout and the speaker context menus needs a home here, because it is the first place a Mac user looks and because it is what makes the app keyboard-navigable and scriptable.

7. The three decisions

QuestionRecommendationCost of the other answer
Overflow menu, or the menu bar?Menu bar for real, toolbar button kept as a shortcutMenu-bar-only is more native but less discoverable for someone crossing from Windows. Button-only will read as a port.
Settings: separate window or full-window page?Separate window at ⌘,Keeping the page is the single most obviously non-native thing left, and ⌘, will feel broken.
Transcript: SwiftUI or AppKit text?NSTextView behind an NSViewRepresentableSwiftUI Text costs per-word hover confidence outright. That is a shipped feature, not a nicety.
